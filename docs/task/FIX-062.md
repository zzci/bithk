# FIX-062 - File restore model: path-correspondence blobs, quarantine rescan, session-safe wipe import

- Status: In Progress
- Plan: -
- Campaign: single BKD issue, worktree mode
- Created: 2026-07-05

## Context (user-reported, production v0.2.1)

1. Downloads of quarantined file rows 500 (`Unknown file storage driver:
   'quarantined:backup-restore-missing-blob'`) — `getDriver()` throws on the sentinel
   (`storage/registry.ts:36`; callers `file.service.ts:755,824`). The promised "clean 404" was
   never implemented on the download path.
2. Copying the old instance's storage tree (`FILE_STORAGE_LOCAL_ROOT`, sharded `ab/cd/<sha256>`)
   onto the new instance does NOT heal quarantined rows — un-quarantine only runs after a blob-
   archive upload; there is no rescan trigger.
3. Wipe import kicks the operator out instantly (users wipe cascades sessions → the admin's
   session dies; UI polls 401 and bounces to login) even though the job continues server-side.

## Product decisions (owner, 2026-07-05)

- **Blob-embedded ("合并") export is retired.** Backups are DB data only. File bytes are the
  operator's responsibility: keep/copy the storage tree (local) or the bucket (S3); restore
  correctness comes from DB-row ↔ storage-path correspondence (content-addressed keys).
- **Import must run as a background job independent of the requesting identity** so a wipe
  import always completes even if the operator's session is invalidated.

## Scope

### A. Quarantine serves 404, never 500

- Download / metadata / thumb / share-public paths: rows whose `storage_driver` starts with
  `quarantined:` → 404 `AppError` code `FILE_CONTENT_UNAVAILABLE` (message hints the blob can be
  restored by putting bytes back + rescan).
- GC/release/drain paths (`file.service.ts:624` area): quarantined rows skip the driver
  `delete` call (no blob to delete) instead of throwing.
- Web: attachment/file list and preview render an "content unavailable" state for such rows
  (detect the 404 code), not a broken preview loop.

### B. Rescan / un-quarantine trigger (path-correspondence heal)

- Reuse `unquarantineRestoredFiles` (blob-restore.ts): expose it as
  - CLI: `backup:blob-rescan` (offline runtime, same wiring as backup:import), and
  - admin endpoint + button in the backup/import panel ("重新扫描缺失文件").
- Run the same rescan automatically at the END of every import apply (so "copy storage dir
  first, then import" heals with zero extra steps).
- Report shape: `{ scanned, healed, stillMissing }`.

### C. Retire blob-embedded export

- Export (web + CLI + export-v2 token route): stop embedding blob bytes; remove the include-blobs
  option from the UI; CLI `--blobs`/`--no-blobs` flag removed (accepted, warned, ignored if
  passed). Manifest keeps a `blobs: "external"` marker.
- Import: KEEP the ability to read old archives that contain blobs (backward compat), and keep
  the blob-restore upload endpoint working for old blob archives.
- Docs (`docs/modules/backup.md` or equivalent + changelog): the supported file story is
  "DB backup + storage tree/bucket copy; keys are content-addressed so paths always correspond".

### D. Session-safe background wipe import

- Verify the apply runner is fully detached from the request (it already runs post-response via
  `startImportApply`; confirm nothing mid-job reads the requester's session).
- Keep the operator logged in across a wipe: capture the current session row before the wipe;
  after archive users insert, re-create the session bound to the archive admin matched by
  id/email/oauthSub (same token → cookie stays valid), inside the same transaction.
- Import job status/report must be readable by ANY admin after re-login (not creator-bound), so
  even a lost session cannot hide the outcome.
- Web import flow: no forced logout during wipe import; progress poll keeps working.

### E. Remove replace mode entirely (owner amendment, 2026-07-05)

Wipe+merge supersedes replace; the two duplicate each other and replace carries the
exact-journal gate bug. Delete it:

- Web apply dialog: merge is the only mode — remove the mode radio; keep just the
  "wipe existing data first" toggle (+ its type-to-confirm).
- API: `applyBodySchema` drops `mode` (or hard-pins `merge`); `prepareReplace`,
  `readLiveSchemaJournal`'s replace gate, the v1 delete-then-insert engine call inside v2 apply,
  and the `INVALID_APPLY_MODE` replace+wipe guard are deleted. 400 with a clear message if an
  old client still sends `mode=replace`.
- CLI: `backup:import` drops `--mode` (merge implied; `--wipe` stays). Passing `--mode` warns
  and is ignored, except `--mode replace` → hard error pointing at `--wipe`.
- The v1 restore surface (`restore.routes.ts` JSON restore), if still mounted, is OUT of this
  amendment's scope — report whether anything still references it instead of deleting.
- Locales/i18n updated; tests for removed paths deleted, replacement guard tests added.

## Acceptance Criteria

- Quarantined row: GET content/metadata/thumb → 404 `FILE_CONTENT_UNAVAILABLE` (route test);
  share-public path same; GC sweep over a quarantined row completes without error.
- Place bytes at the content-addressed path → CLI rescan (and admin endpoint) flips the row back
  to its real driver; download 200 with correct bytes. Import-apply end runs the same rescan.
- Export archives contain no blob bytes; old blob-bearing archives still import; blob-restore
  upload still works.
- Wipe import via web: operator session survives (same cookie works after completion), job
  completes and report is visible; CLI wipe import unaffected.
- No route removals; regenerate api docs/spec/types for changed schemas; `bun run check` EXIT 0.
