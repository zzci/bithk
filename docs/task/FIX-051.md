# FIX-051 - Pin GitHub Actions to commit SHAs (P2 supply chain)

- Status: Planned
- Plan: [PLAN-100](../plan/PLAN-100.md)
- Campaign: `l1-bithk-audit-20260701145456`
- Owner: L3
- Created: 2026-07-01

## Summary

CI/release workflows pin third-party actions to floating tags. A retagged/compromised action version could
inject code into CI; `release.yml` is highest risk (`contents: write` + `GITHUB_TOKEN`). Pin to full commit
SHAs. See AUDIT-20260701.md → P2.

## Acceptance Criteria

- All **third-party** (non-`actions/*`) `uses:` in `.github/workflows/release.yml` and `.github/workflows/ci.yml`
  are pinned to a 40-char commit SHA with a trailing `# vX.Y.Z` comment recording the human-readable version.
  At minimum every action in `release.yml`.
- First-party `actions/*` may stay at major tags (lower risk) but pinning them too is acceptable.
- Each pinned SHA must correspond to the tag it replaces (verify the SHA belongs to that version's ref — do
  not invent SHAs). If a SHA cannot be verified offline, report `blocked` rather than guessing.
- Workflows remain syntactically valid; no behavior change other than the pin.
- Renovate/Dependabot compatibility preserved (the `# vX` comment enables auto-bump).

## Files in Scope

- `.github/workflows/release.yml`
- `.github/workflows/ci.yml`

## Design constraints

- Do not change job logic, permissions, triggers, or the `check` gate.
- If network access to resolve tag→SHA is unavailable in the worktree, report `blocked` with the list of
  actions needing resolution instead of committing unverified SHAs.
