# FIX-046 OIDC session expires after access-token TTL (~1h) instead of session max-age

- **status**: completed
- **priority**: P1
- **owner**: pma
- **createdAt**: 2026-06-19 12:55
- **completedAt**: 2026-06-19 13:26

## Description

Logged-in users on an OIDC deployment are forced to re-authenticate after the
IdP access-token lifetime (commonly ~1 hour), even though the session cookie
and `SESSION_MAX_AGE` are configured for 24 hours.

### Root cause

Two independent expiry clocks disagree, and the shorter one silently wins:

1. **Browser cookie** — `writeSessionCookie` uses `maxAge = authCfg.sessionMaxAge`
   (`auth.routes.ts:488`), currently `settings.session.max_age = 86400` (24h).
2. **Server session row** — `createSession` writes
   `expiresAt = now + (expiresIn ?? 3600) * 1000` (`auth.service.ts:394`), where
   `expiresIn` is the IdP access-token `expires_in` passed at `auth.routes.ts:485`
   (and the TOTP path `auth.routes.ts:841`). So the real login lifetime equals the
   IdP access-token TTL (often 1h, or the `?? 3600` fallback when absent).

Every request runs `oauthSessionAuthProvider` (`auth.service.ts:492`); once the
server row is expired it can only refresh when `session.refreshToken` exists.
But the authorize request hard-codes `scope = "openid profile email"`
(`oidc.ts:134`) with **no `offline_access`**, so the IdP issues no refresh token,
`refreshToken` is null, and the code hits the teardown branch
(`auth.service.ts:504-506`) → `deleteSession` + `clearSessionCookie` → forced logout.

Corroborating inconsistency: the **single-user** path already passes
`authCfg.sessionMaxAge` as the 5th `createSession` argument (`auth.routes.ts:711`),
so single-user logins correctly last 24h while OIDC logins die at the token TTL.
The fix generalizes the single-user path's correct intent to all paths.

## Acceptance criteria

- An OIDC session stays valid for `SESSION_MAX_AGE` (24h by default), not the
  IdP access-token TTL.
- When the access token expires mid-session and a refresh token is present, it
  is refreshed in the background; the user is not logged out.
- When no refresh token is present (or a refresh fails), the user remains logged
  in until the session max-age is reached — they are not torn down at the
  access-token TTL.
- The session max-age is a hard ceiling: at 24h the session is torn down and the
  user re-authenticates.
- The authorize request requests `offline_access` so cooperating IdPs issue a
  refresh token.
- A regression test reproduces the bug: access token expired + no refresh token
  + within session max-age → user is still resolved (not logged out).

## ActiveForm

Decoupling application session lifetime from the IdP access-token TTL and adding
background refresh.
