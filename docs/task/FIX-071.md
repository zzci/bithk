# FIX-071 - Project list issues one profile request per ship card

- Status: Proposed
- Plan: -
- Depends on: [REFACTOR-039](REFACTOR-039.md) (merge first — the list and card were rewritten by it)
- Created: 2026-08-28

## Goal

After the projects-as-sections fold, a ship project's list card renders its
maritime particulars (hull number, IMO/MMSI, spec rows) by fetching the ship
profile per card. A page of 20 ship projects therefore issues 20 extra
requests on top of the list query.

Each request is a cheap indexed lookup and the current fleet is ~22 ships, so
this is a latency and request-count defect, not an outage. Fix it by embedding
a profile summary on the list row rather than by caching or batching on the
client.

## Scope

- API: `GET /projects` list rows carry a small profile summary for projects
  with the `ship-profile` section mounted (hull number, ship status, and the
  handful of fields the card renders) — resolved in the same batch pass the
  list already does for section sets, not per row.
- Web: the ship card reads the summary from the list payload; the per-card
  profile query is deleted.
- Regenerate api-spec / api-types.

Out of scope: a generic per-section list-row projection mechanism. One
section needs this today; add the abstraction when a second one does.

## Verification

- One request renders a full page of ship cards (assert query count in the
  list test, or assert the card renders with the profile endpoint mocked to
  fail).
- The list query issues no per-project profile lookup (no N+1) — same batch
  assertion style as the section-set load.
- Cards for general projects are unchanged.
- `bun run check` EXIT 0.
