# FIX-041 Backup import rejects empty-string id sentinel (drive root entries)

- Status: Completed
- Plan: -
- Owner: local-session
- Updated: 2026-06-16

## Goal

A real end-to-end test of the FEAT-033 backup CLI (seed a rich dataset →
`backup:export` → `backup:import` into a fresh DB) failed at import with
`Invalid id format on field parentEntryId`. Make a full real-data backup
round-trip import cleanly.

## Root cause

`assertIdShape` (`apps/api/src/modules/backup/restore.service.ts`) validates any
`id` / `*Id` / `*_id` field against `RE_SAFE_ID = /^[\w-]{1,128}$/`, which
requires at least one character. `drive_entries.parent_entry_id` uses the empty
string `""` as the "no parent / root" sentinel, so every backup containing a
root drive entry was rejected. This is shared import validation (the HTTP
`/backup/v2/imports` path hits it too); the bug was latent because the FEAT-033
e2e only seeded an admin + settings and never exercised drive hierarchy.

## Scope

- `apps/api/src/modules/backup/restore.service.ts`: in `assertIdShape`, treat an
  empty string like null/absent (skip it) so the root sentinel imports.
- `apps/api/src/modules/backup/restore.service.test.ts`: unit tests locking the
  empty-string acceptance and continued rejection of unsafe formats.
- `tests/e2e/modules/backup/cli-roundtrip.test.ts`: seed a root drive entry
  (`parent_entry_id = ""`) into the source DB and assert it round-trips.

Out of scope: backup *completeness* gaps surfaced by the same test
(`global_procurement_categories` not registered in any backup contribution;
`document_pins` debatable) — reported separately for a decision.

## Acceptance

- `assertIdShape` accepts `""` on id-like fields, still rejects unsafe formats.
- A full real-data round-trip imports with exit 0 and no rows lost for backed-up
  tables; the root drive entry keeps `parent_entry_id = ""`.
- `bun run check` passes.
