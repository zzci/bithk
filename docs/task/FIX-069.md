# FIX-069 - Attachment inline preview blocked by CORS on presigned R2 redirect

- Status: Completed
- Plan: -
- Created: 2026-07-08

## Problem (user-reported)

Opening an attachment preview on a deployment backed by Cloudflare R2 fails
with a CORS error:

> The value of the 'Access-Control-Allow-Credentials' header in the response
> is '' which must be 'true' when the request's credentials mode is 'include'.

The bucket CORS policy is fine — a preflight probe shows
`Access-Control-Allow-Origin: <app origin>` with `GET, PUT` allowed. The
failure chain is client-side:

1. The preview fetch uses `credentials: "include"` (explicit in
   `attachment-section.tsx`, global in `httpRaw`).
2. The API 302s to a presigned S3/R2 URL (FEAT-052,
   `file.service.ts` `buildDownloadResponse`).
3. `fetch` carries its credentials mode across the redirect; `include` makes
   the browser require `Access-Control-Allow-Credentials: true` on the
   cross-origin response.
4. R2's CORS policy has no credentials field and never emits that header
   (AWS S3 emits it for non-wildcard origins; R2 does not), so the bucket
   cannot be configured around this.

CSS `background-image` thumbnails are unaffected (no CORS check); only
explicit blob fetches (attachment preview dialog, drive preview via
`httpRaw`) hit it.

## Fix

The web app and API are same-origin (`BASE_URL` is the `/api` path prefix),
so `include` was never needed — the default `same-origin` mode sends cookies
to the API exactly as before, and after the 302 to the storage origin the
request becomes non-credentialed, so the CORS check only requires the
already-present `Access-Control-Allow-Origin` match.

- `shared/lib/http.ts`: `httpRaw` `credentials: "include"` → `"same-origin"`.
- `attachment-section.tsx`: drop the explicit `credentials: "include"` from
  the preview fetch (default is `same-origin`).

## Verification

- Web unit tests + `bun run check` green.
- Manual: attachment preview on an S3-backed deployment loads without CORS
  errors.
