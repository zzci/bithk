# FIX-048 - Drive confirm-upload uploader-scoped dedup (P1 IDOR)

- Status: Completed
- Plan: [PLAN-100](../plan/PLAN-100.md)
- Campaign: `l1-bithk-audit-20260701145456`
- Owner: L3
- Created: 2026-07-01

## Summary

`confirmDriveUpload` bypasses the uploader-scoped instant-dedup that `presignDriveUpload` applies, letting an
authenticated user who knows a victim file's sha256 attach and download the victim's blob (cross-user IDOR),
and register a `files` row whose bytes may not match the content-addressed key. See AUDIT-20260701.md → P1.

## Root cause

- `presignDriveUpload` (`apps/api/src/modules/drive/drive.service.ts:447`) scopes dedup to the uploader via
  `findStoredBlob(db, sha256, input.createdBy)`.
- `confirmDriveUpload` (`drive.service.ts:482-509`) calls `registerUploadedBlob` directly, which dedups on
  `(sha256, storage_driver)` only — no `uploadedBy` filter (`apps/api/src/modules/file/file.service.ts:437-439`).

## Acceptance Criteria

- In the confirm path, a blob whose `(sha256, driver)` row already exists but was uploaded by a **different**
  user is NOT attached to the caller: reject (or force a fresh authenticated PUT) instead of reusing the row.
  The same-uploader case still dedups (no regression to legitimate re-confirm).
- Quota accounting unchanged for the legitimate paths; no double-count.
- A regression test: user B calling confirm-upload with user A's sha256 (object present in storage) must NOT
  yield a downloadable entry for B (expect rejection); user A re-confirming their own upload still works.
- `bun run check` passes.

## Files in Scope

- `apps/api/src/modules/drive/drive.service.ts` (`confirmDriveUpload`)
- `apps/api/src/modules/file/file.service.ts` (`registerUploadedBlob` / a scoped variant, `findStoredBlob`)
- Co-located tests: `apps/api/src/modules/drive/*.test.ts`, `apps/api/src/modules/file/*.test.ts`

## Design constraints

- Preserve the content-addressed storage dedup invariant `UNIQUE(sha256, storage_driver)` at the storage
  layer; the fix is about who may *attach/reference* an existing blob, not about storing duplicates.
- Match the existing FEAT-044 security rationale documented at `file.service.ts:350-356,371-379`.
- No new env knobs; minimal surface.
