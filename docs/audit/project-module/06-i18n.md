# Project Module Audit — Lane 06: i18n

P0 0 · P1 0 · P2 2 · P3 2

Scope: en/zh locale parity for the `projects` and `drive` namespaces (the project
module's Files tab consumes `drive`), plus the project-module React components.
i18n is `react-i18next` with a Vite `import.meta.glob` lazy backend; each
`(locale, namespace)` is a JSON shard under `apps/web/src/locales/<lng>/<ns>.json`
(`apps/web/src/app/i18n.ts:9-65`). Languages and namespaces are derived from the
filesystem (`apps/web/src/app/i18n.ts:30-46`), so adding a key in `en/` without a
matching `zh/` entry does NOT raise an error — it silently falls back to English
(`fallbackLng: "en"`, `fallbackNS: "common"`, `load: "languageOnly"`,
`apps/web/src/app/i18n.ts:127-137`). That fallback is exactly why the defects
below present as "English text shown inside the Chinese UI" rather than as missing
-key crashes.

---

## F1 — `zh/drive.json` has 7 untranslated (English) values — P2 medium

Location:
- `apps/web/src/locales/zh/drive.json:30` — `browser.uploadFolder` = `"Upload folder"`
- `apps/web/src/locales/zh/drive.json:99` — `browser.action.versions` = `"Version history"`
- `apps/web/src/locales/zh/drive.json:203` — `versions.title` = `"Version history"`
- `apps/web/src/locales/zh/drive.json:204` — `versions.description` = `"Versions for {{name}}."`
- `apps/web/src/locales/zh/drive.json:205` — `versions.empty` = `"No versions yet"`
- `apps/web/src/locales/zh/drive.json:206` — `versions.current` = `"Current"`
- `apps/web/src/locales/zh/drive.json:207` — `versions.switch` = `"Make current"`

Compare the English source: `apps/web/src/locales/en/drive.json:30`,
`:99`, `:202-208`. The keys exist in both locales (no missing keys), but the
Chinese values were never translated — they are verbatim English. Every other
`zh/drive.json` value is properly translated (e.g. `browser.newFolder` "新建文件夹",
`browser.action.move` "移动"), which makes the untranslated entries stand out.

Impact: Chinese users see English strings mixed into the Drive UI and the file
version-history dialog. Because the project module's Files tab renders under the
`drive` namespace, these leak into the project detail view too. The entire
`versions.*` block (the version-history dialog) is English for Chinese users.

Recommended fix (described, NOT applied): translate the 7 values in
`apps/web/src/locales/zh/drive.json`, e.g. `uploadFolder` → "上传文件夹",
`action.versions` / `versions.title` → "版本历史", `versions.description` →
"{{name}} 的版本。", `versions.empty` → "暂无版本", `versions.current` → "当前版本",
`versions.switch` → "设为当前版本". Keep the `{{name}}` placeholder intact in
`versions.description`. Consider adding a CI parity check (see F4) that flags
`zh` values byte-identical to their `en` counterparts for ASCII-only strings.

## F2 — English plural forms not handled for `{{count}}` interpolations — P3 low-nit

Location (representative, `apps/web/src/locales/en/`):
- `projects.json:37` — `list.total` = `"{{count}} projects"`
- `projects.json:165` — `issues.total` = `"{{count}} work orders"`
- `projects.json:221` — `procurement.total` = `"{{count}} records"`
- `projects.json:207-208` — `issues.due.inDays` / `issues.due.overdue`
- `drive.json:48` — `browser.selectedCount` = `"{{count}} selected"`

These use a single form with `{{count}}`. i18next supports CLDR plurals via
`_one` / `_other` suffixed keys, but none are defined. With `count = 1` English
renders the grammatically wrong "1 projects" / "1 work orders" / "1 records" /
"1 selected".

Impact: minor English grammar polish only. Chinese is unaffected (no plural
inflection), and counts of 1 are an edge case. Cosmetic.

Recommended fix (described, NOT applied): for the English shards add plural
variants, e.g. `"list.total_one": "{{count}} project"`,
`"list.total_other": "{{count}} projects"` (repeat for `issues.total`,
`procurement.total`, `browser.selectedCount`). i18next selects the form from
`count` automatically; call sites already pass `{ count }` so no component
change is required. `zh` needs only the `_other` form. Low priority for the dev
phase.

## F3 — `projects` namespace duplicates the `issues.status` / `issues.group` blocks verbatim — P3 low-nit

Location: `apps/web/src/locales/en/projects.json:184-197` (and the identical
`zh/projects.json:184-197`). `issues.status` (lines 184-190) and `issues.group`
(lines 191-197) contain byte-identical key/value pairs (todo/working/review/
done/cancel) in both locales.

Impact: maintenance hazard, not a user-facing defect — a future label change to
one block can silently diverge from the other and the two are visually
indistinguishable. Pure duplication (≈14 lines × 2 locales).

Recommended fix (described, NOT applied): if `group` labels are always equal to
`status` labels, drop the `group` block and have the Kanban column code read
`issues.status.<key>`; or keep both but add a comment noting they must stay in
sync. Defer unless the duplication is actually causing drift.

## F4 — No automated en/zh key-parity / untranslated-value guard — P2 medium

Location: locale infrastructure — `apps/web/src/app/i18n.ts` derives namespaces
from the filesystem but performs no cross-locale completeness check; there is a
locale test harness (`apps/web/src/shared/components/i18n-locale.test.tsx`,
`apps/web/src/test/i18n.ts`) but it did not catch F1.

Description: because missing/untranslated keys fall back silently to English
(`i18n.ts:127,130,137`), parity defects like F1 ship undetected. There is no
build/test gate that (a) asserts every `en/<ns>.json` key exists in `zh/<ns>.json`
(and vice versa), or (b) flags `zh` values that are byte-identical to their `en`
source for ASCII-only strings (a strong "forgot to translate" signal).

Impact: F1-class regressions recur with every new feature. This is the root
cause that lets the F1 leaks persist.

Recommended fix (described, NOT applied): add a Vitest spec that loads every
`en/*` and `zh/*` shard, deep-diffs key sets per namespace (fail on asymmetry),
and warns when a `zh` leaf value equals its `en` value and is pure-ASCII.
Wire it into `bun run check`. This converts F1/F2 from manual-review findings
into CI-enforced invariants.

## Clean areas (checked, no issues)

- **`projects` namespace key parity** — `apps/web/src/locales/en/projects.json`
  vs `zh/projects.json`: full structural parity (both 422 lines, identical key
  tree across `page/toast/list/status/field/tags/cover/create/edit/delete/detail/
  settings/tabs/overview/issues/procurement/members/roles/capability/
  capabilityGroup/categories/dangerZone`). Every `zh` leaf is properly translated.
  No missing keys, no extra keys.
- **`overview` namespace** — `en/overview.json` vs `zh/overview.json` (both 11
  lines): full parity, all values translated, `{{name}}` placeholder consistent.
- **Interpolation parity** — every placeholder used in `en` (`{{count}}`,
  `{{name}}`, `{{done}}`, `{{total}}`) is preserved with the same token in the
  corresponding `zh` value across `projects`, `drive`, and `overview`. No
  interpolation-variable mismatches between locales (the F1 untranslated values
  still keep their `{{name}}` token, so no runtime placeholder breakage).
- **Locale-appropriate formatting differences are intentional, not defects** —
  e.g. `settings.projectId` "Project ID: " (trailing ASCII space) vs "项目ID："
  (fullwidth colon) is correct per-locale punctuation, not a parity bug.
- **`common` namespace en/zh parity** — `apps/web/src/locales/en/common.json`
  vs `zh/common.json` (both 74 lines): full key parity across
  `theme/auth/common/nav/search`, every `zh` leaf translated. The project
  module consumes `common:common.error.operationFailed`,
  `common.error.loadFailed`, `common.prev`, `common.next`
  (`apps/web/src/app/routes/_app/projects/index.lazy.tsx:82,106,162-163,172`) —
  all present and translated in both locales.
- **No hardcoded user-facing string literals in project-module components** —
  a grep across `apps/web/src/app/routes/_app/projects/*.tsx` for literal
  `toast.success("…"` / `toast.error("…"`, `aria-label="…"`, and
  `placeholder="…"` (i.e. quoted strings instead of `{t(...)}`) returned **no
  matches**. All toasts, ARIA labels, and placeholders are routed through
  `t(...)`. 20 project-module files import `react-i18next`. (Caveat: this
  pattern-grep does not cover bare JSX text nodes like `<span>Text</span>`; none
  were spotted in the files read, but a full JSX-text line-scan was not run.)
