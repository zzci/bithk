## P1 — Fix promptly (source-verified)

### [HIGH] Drive `confirmDriveUpload` bypasses the uploader-scoped dedup → cross-user file disclosure (IDOR)
`apps/api/src/modules/drive/drive.service.ts:482-509` + `apps/api/src/modules/file/file.service.ts:431-444`

- **Root cause.** The presigned direct-upload feature (FEAT-044) deliberately scopes instant-dedup to the
  uploader: `presignDriveUpload` calls `findStoredBlob(db, sha256, input.createdBy)` (`drive.service.ts:447`)
  because the content-addressed key is the **client-declared** sha256 and is never server-verified. But
  `confirmDriveUpload` skips that guard: it only `statStoredBlob(sha256)` (existence-only HEAD, unscoped)
  then `registerUploadedBlob`, which dedups on `(sha256, storage_driver)` **with no `uploadedBy` filter**
  (`file.service.ts:437-439`).
- **Exploit.** An authenticated attacker who knows a victim file's 64-hex sha256 → `POST` confirm-upload
  targeting their own drive folder (no bytes uploaded) → `stat` finds the victim's already-stored object →
  `registerUploadedBlob` bumps refcount on the victim's `files` row and creates a `file_reference` owned by
  the attacker's new entry → attacker downloads the victim's bytes via `GET /drive/entries/:id/content`.
  Also enables quota-free attach.
- **Severity = HIGH (not CRITICAL):** requires knowing the target sha256. Not in user-facing JSON, but the
  thumbnail `ETag: "<sha256>-w<width>"` (`file.service.ts:745`) leaks hashes of previewable images.
- **Fix direction.** Carry presign's uploader scoping into confirm: before `registerUploadedBlob`, if a
  `files` row for `(sha256, driver)` exists with `uploadedBy !== input.createdBy`, reject and require a fresh
  PUT (re-upload overwrites the content-addressed object, dedup invariant preserved). Equivalent: a
  short-lived per-user pending-upload record created at presign, and confirm only attaches blobs that user
  actually uploaded.
- **Related [MEDIUM]** (`file.service.ts:350-356`, `drive.service.ts:489-508`): confirm HEADs for size but
  never re-hashes, so the content-addressed key can be poisoned (key content ≠ key name). Enabling primitive
  for the HIGH; the uploader-scoping fix closes it. → FIX-048.

## P2 — High priority

### [MEDIUM] Auth IP rate-limiter is inert in the default same-host-proxy deployment
`apps/api/src/modules/account/auth/auth.routes.ts:140-147,278,338,625,751`

The per-IP limiter exempts all loopback source IPs, but with the default `TRUST_PROXY=false`
(`config/schema.ts:56`) `getClientIp` returns the socket peer (`client-ip.ts:40-42`). A reverse proxy on
the same host connecting over loopback makes every `/login`, `/callback`, `/login-local`, `/totp/verify`
look like `127.0.0.1` → IP throttling fully disabled. Account-level lockouts still backstop credential
guessing (defense-in-depth degradation, not a full brute-force hole). **Fix:** do not exempt loopback when
`TRUST_PROXY=false`; or promote "proxy-on-loopback with `TRUST_PROXY=false`" to a boot warning. → FIX-049.

### [MEDIUM] S3 orphan sweep only inspects the first 1000 objects
`apps/api/src/modules/file/storage/s3.ts:110-111` (via `s3-sweep.ts:29`)

`driver.list("")` issues a single `maxKeys:1000` with no continuation-token loop; buckets with >1000 objects
never reclaim orphaned/aborted direct-upload blobs beyond the first page — unbounded storage/cost leak, and
FEAT-044's "reclaim aborted uploads" goal silently fails at scale. Not a deletion hazard (the `inArray`
guard is scoped to the same 1000 keys). **Fix:** loop the continuation token in `list`, or page the sweep. → FIX-050.

### [MEDIUM] GitHub Actions pinned to floating tags, not commit SHAs
`.github/workflows/ci.yml` + `release.yml` (all third-party `uses:`)

`docker/build-push-action@v7`, `trufflesecurity/trufflehog@v3.95.5`, `aquasecurity/trivy-action@v0.36.0`,
etc. are floating tags. A retagged/compromised version injects CI code; `release.yml` is highest risk
(`contents: write` + `GITHUB_TOKEN` for release upload). **Fix:** pin third-party actions to 40-char commit
SHAs (`@<sha> # vX`), especially in `release.yml`; let Renovate/Dependabot bump. → FIX-051.

## P3 — Record / opportunistic (bundled → FIX-052)

- **[LOW] service-token compare short-circuits on length** `shared/middleware/service-token.ts:35` — `a.length !== b.length` before `timingSafeEqual` leaks configured token length. Fix: hash both sides to fixed width first (match the PAT path).
- **[LOW] backup-staging sweep not stopped on shutdown** `index.ts:78-88` vs `backup/export-job.service.ts:290` — `stopBackupStagingSweep()` exported but never called in `closeServices`; timer is `.unref()`'d so no hang, but an in-flight `rmSync` at SIGTERM is neither awaited nor cancelled. Fix: add `await safe("stopBackupStagingSweep", …)`.
- **[LOW] file-GC sweep has no re-entrancy guard** `file/gc.ts:51-82` — overlapping ticks possible if a sweep exceeds the interval; deletes are idempotent (`id=? AND refCount=0`) so low risk. Fix: add an in-flight boolean mirroring `audit/retention.ts`.
- **[LOW] two client redirects skip scheme validation** `web/src/app/routes/denied.tsx:108` (logout-url) and `totp-verify.tsx:38` (redirect) — server-owned URLs placed into `href`/`location` with no `https://`/`/` check; near-zero risk but inconsistent with `login.tsx:36` `isSafeRedirect`. Fix: route both through `isSafeRedirect`.
- **[LOW] dead `requireTotp` step-up path** `shared/middleware/totp.ts:5` + `account/users/totp.service.ts:256-273` — `POST /account/me/totp/verify` mints a single-use step-up token, but its only consumer `requireTotp` is never mounted (zero importers). Issues tokens that gate nothing → false impression of a sensitive-op gate. Decision needed: wire it onto sensitive ops, or remove issuance+middleware.
- **[LOW] dead `DB_ENCRYPTION` env** `.env.docker:20` not in the zod schema (`config/schema.ts`) and read nowhere; zod strips it silently so `DB_ENCRYPTION=true` yields no encryption and no error. Fix: remove the line (or implement the flag).
- **[LOW, deferred] docker-compose runs as root** `docker-compose.yml:15-16` `user:"0:0"` — documented local-test-only choice; production image (`Dockerfile:35`) correctly `USER bun`. Left as-is; noted for revisit with a fixed UID + chown.

## Coverage gaps (need runtime/専項 verification — not proven pass)

1. **⚠ Highest residual risk:** the global `policyMiddleware` object-level engine is only declared for
   `contact`/`document`/`drive`. `project`/`issue`/`ship`/`hr`/`procurement`/`item` write routes rely on
   per-route `authRequired` + service-layer ownership, not the engine. The boot assertion only proves the
   registry is non-empty. A write route mounted behind `authRequired` alone (no `requirePermission`, no
   service owner check) would be an invisible horizontal-authz hole. **Recommend a targeted row-level
   ownership audit of project/issue/ship/hr/procurement write handlers** (candidate follow-up campaign).
2. `apps/web` has **no coverage gate in CI** (coverage step is `working-directory: apps/api`); function
   floor 70% < the 80% project standard.
3. Real S3/R2 presign Content-Type binding (prevents PUT type swap) unverified — tests use an in-memory fake.
4. Univer hyperlink-cell XSS is the engine's escaping boundary (out of app-code scope) if sheets carry
   user-authored hyperlink cells.
5. PAT `tokenModuleForPath` prefix-map completeness and `pid-lock` PID-recycle/port-rebind race: logic reads
   sound but not exhaustively proven.
