## Fixtures Strategy

Local DB data is not reliable for visual review. Stage C/D/E/F should use test-scoped API mocks, not real seeds.

| Fixture | Path | Coverage |
| --- | --- | --- |
| Ships | `tests/fixtures/ships.ts` | Multiple lifecycle stages, archived state, equipment categories/statuses, bound projects, templates, maintenance orders, issue references. |
| Projects | `tests/fixtures/projects.ts` | Active/archived projects, tags, capabilities, members, roles, procurement categories, issues across statuses/priorities, procurements across every status. |
| Contacts | `tests/fixtures/contacts.ts` | Public/private, confidential managed, confidential masked, active/inactive, tags, missing optional fields. |

Reusable pattern for Playwright route tests:

1. Intercept `/api/**`.
2. Strip `/api` from the request path.
3. Call `shipsFixtureResponse(path, params)`, `projectsFixtureResponse(path, params)`, then `contactsFixtureResponse(path, params)`.
4. Fulfill matched payloads; return a test 404 for unmatched paths so new UI dependencies are explicit.

Do not seed the real DB for parity screenshots unless L2/L1 approve a separate backend-owned dev-data task.
